# Avara account transition
Existing MongoDB listings, rentals, messages and role records stay intact. Supabase is the identity provider when AVARA_AUTH_PROVIDER=supabase. New accounts verify their email before Mongo profile creation, with role user only. Never link a legacy profile by email alone. Migrate existing identities deliberately with ownership checks and an administrator-reviewed mapping of Supabase UUID to Mongo ObjectId before cutover; do not switch existing production until mapped. New registrations remain legacy by default. Provider access token is HTTP-only, checked against /auth/v1/user on protected requests; access expires at at most one hour and user signs in again (refresh-token rotation not implemented). No service key is used by auth. Email recovery token is verified then password updated with that access token; no reset session is issued to the browser. Configure email confirmation and recovery templates in dedicated project: confirmation link {{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }} and recovery link {{ .SiteURL }}/auth/reset-password?token_hash={{ .TokenHash }}. Set verified production Site URL and redirect allowlist, custom SMTP, rate limits and CAPTCHA before broad release. Do not store raw tokens, passwords or secret keys in source/logs. Verify delivery and token replay/expiration, login, logout, reset, existing user migration, and role checks on staging. CMS still requires existing migration and server-only service role/anon keys. Mongo is still the transactional data store; no production database migration performed. Super-admin only grants admin; no UI grant of super-admin; cannot modify super-admin or own account; deletion is disabled pending a safe cross-store deletion procedure. Existing CMS controls homepage, collections and neighbourhoods, journal and developments; global media, navigation, SEO settings, audit trail and granular permission matrix are still outstanding.
