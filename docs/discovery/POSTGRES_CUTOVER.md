# PostgreSQL-only Avara cutover
Decision: Supabase Auth + PostgreSQL + Storage, no MongoDB or Mongoose after cutover. This branch is a foundation, not a completed migration. The live application still uses MongoDB; no Supabase organization/project for Avara was accessible and no live records were transferred.
## Clean start decision
The owner requested a fresh PostgreSQL database rather than importing historical MongoDB records. Preserve the old database without deleting it; no legacy account linking, password migration or historical imports are required for the initial fresh deployment. Existing users must register anew. Do not switch live traffic until all retained routes are replaced. Avara organization ID: doemcximflwzrqssfrkg; the connected account has not yet granted access. Never substitute the Freshpick project.
## Scope
Keep discovery, listings, saved properties, owner enquiries, three role workspaces and CMS. Existing booking/payment/rental/maintenance/financial routes must either be migrated with explicit acceptance tests or retired/archived deliberately; don't silently drop records. Defer AI concierge and advanced operations; retain external read-only discovery.
## Replacement order
1. Dedicated project in Avara organization, enable verified Auth, configure custom SMTP, create CLI migration from validated schema candidate (CLI unavailable here). Review database advisors, RLS and grants. No Freshpick reuse.
2. Only if the owner subsequently requests historical import: export read-only Mongo inventory and private account mappings in a protected environment; verify counts, foreign keys, statuses and duplicates. Map legacy user ObjectIds to verified Supabase UUIDs with administrator-reviewed identity ownership; never auto-link by email. Preserve property ObjectId strings as URLs, new properties may use UUIDs. Do not export password hashes to PostgreSQL; require secure Auth migration or recovery. Keep private addresses separate.
3. Replace auth profile access, all property search/detail/create/edit/moderation, favorites, messages, dashboards and CMS integrations together. The independent PostgREST reader here is not wired into production yet, to prevent split reads/writes. Add transactional message send/block, moderation audit and manager approval, role guards, image Storage policies and access token refresh. Reconcile retained bookings/rents before switch.
4. For the clean start, verify the isolated empty database, register and verify fresh test accounts, test permissions and core journeys with actual Supabase, then switch all retained routes in one deployment. Keep legacy data untouched. If a historical import is later requested, freeze legacy writes during import and reconcile records first. Rollback before accepting new writes; no untracked dual writes. Keep encrypted read-only backups per retention policy.
5. Delete Mongoose models/services, custom JWT/password code and Mongo tests/env only after every retained route is PostgreSQL-backed. Regenerate npm lockfile with npm uninstall mongoose; enforce CI scan for Mongo imports and variables, run npm audit, browser/SQL tests and production smoke tests. Remove unused internal AI/operational modules only after confirming no navigation or records depend on them.
## Schema
Eight proposed tables: profiles, properties, private property details, favorites, conversations, messages, conversation blocks, moderation events. Existing CMS tables remain. RLS plus explicit grants: anonymous active public listing columns only; own profiles and favorites, participant-only conversations; role updates, approval, private details and sends server-only. No live DB test or migration applied; plain PostgreSQL CI runs with a minimal Auth fixture and does not substitute for hosted Supabase tests.
